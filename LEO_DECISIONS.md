# LEO Engineering Decisions

| # | Decision | Rationale | Date |
|---|----------|-----------|------|
| 1 | Python 3.12 + asyncio modular monolith; SQLite/WAL | Matches plan recommendation, zero extra infrastructure, easy local recovery and inspection. | 2026-11-18 |
| 2 | Virtualenv at `.venv` managed by `uv` | Reproducible installs, Python 3.12 available locally, no system pollution. | 2026-11-18 |
| 3 | Provider endpoint/model from real environment config; `mock` provider for tests | Plan forbids invented endpoints, credentials or model IDs. | 2026-11-18 |
| 4 | Secrets are env-var *names* in config; never values | Prevents credential leakage into config, prompts, logs and API responses. | 2026-11-18 |
| 5 | Pydantic v2 contracts in `leo/contracts.py` | Stable interfaces for parallel module development without circular imports. | 2026-11-18 |
| 6 | Durable task state in SQLite with evidence requirement | Protects against false completion and unsafe replay. | 2026-11-18 |
| 7 | External ecosystem capabilities are reimplemented natively or via narrow adapters, no source copying | License safety and functional integration rather than superficial imitation. | 2026-11-18 |
| 8 | SKILL.md availability gates are stored separately from permissions and dependencies | Legacy ecosystem gates hide skills when prerequisites are absent; mapping them to grants or registry dependencies is both wrong and insecure. | 2026-11-18 |
| 9 | Webhook verification fails closed; HMAC covers exact raw bytes | Default no-secret configuration previously accepted arbitrary messages. | 2026-11-18 |
| 10 | Non-loopback API binds require `LEO_API_TOKEN`; local-only remains tokenless | Keeps the product usable locally while removing an unauthenticated remote-control surface. | 2026-11-18 |
| 11 | Imported external skills are inert until a sandboxed execution model exists | Parsing SKILL.md is not evidence that third-party scripts are safe or runnable. | 2026-11-18 |
| 12 | Reasoning effort is resolved per turn (session > global > config), translated per provider, and clamped downward; display uses only provider-declared summaries | Raw chain-of-thought is never shown or persisted; an unsupported level must not escalate cost, and a refused disable steps up to the lowest real effort rather than accepting the provider's default. | 2026-11-24 |
| 13 | Agent-authored skills are documentation-only and stored in the database (`skills`, `skill_files`), never as executable handlers | Extends decision 11 to LEO's own learning loop: self-improvement must not introduce a code-execution surface. Durable bundle content is also available to every surface without a second filesystem source of truth. | 2026-11-24 |
| 14 | `skill_manage` writes are MEDIUM risk and delete is HIGH; native skills are read-only to the agent | Bounded, reversible, audited authoring; a deleted skill has no undelete on the tool surface. Every write requires a fresh `skill_read` of the exact target first. | 2026-11-24 |
| 15 | Post-turn review is proposal-only, bounded, and dispatches through the real tool executor | A review is not a delegated task: it has its own trigger, transcript bounds, tool scope, artifact and audit row. It cannot widen its own authority, cannot accept approvals, and a no-op review is a successful outcome. Memory notes go through `LearningEngine.propose`; skills go through `skill_manage`. | 2026-11-24 |
| 16 | Background skill writes are staged by default; interactive writes are direct | A review's write is the exact `skill_manage` payload in `kv`, bound to an arguments digest and replayed once through the same tool after `/skills approve`. The queue is bounded, rejection is terminal, approve/reject require an operator principal, and delete is never staged (it keeps the HIGH-risk approval). Foreground turns stay interactive so a visible edit is not silently queued. | 2026-11-24 |
| 17 | The skill curator is deterministic and never deletes content | `active -> stale -> archived` is a reversible state transition driven by durable usage counters and an interval+idle gate; native and pinned skills are exempt. A first observation seeds the clock and defers one full interval, so a fresh install is never pruned before review. LLM consolidation, when added, must produce proposals, not automatic rewrites. | 2026-11-24 |
| 18 | Rollback restores one bounded before-state; consolidation is a report | Each authored mutation records at most 10 snapshots per skill in `kv` (full package before version replace/delete, one file before file write/removal); rollback replays the normal write path under a restoring flag, so validation and audit still apply. Near-duplicate grouping is deterministic and read-only; no automatic merge. | 2026-11-24 |
| 19 | LLM consolidation is opt-in and only stages a multi-operation plan | The model receives a deterministic candidate group and returns strict JSON; the planner validates names, the 60-character description, content/path/secret hygiene and the absorbed subset, then stages `read`/`manage`/`archive` operations. `/skills approve` replays them; nothing rewrites content automatically, native skills never enter a group, and archive is reversible. `/journey` is a read-only timeline over authored skills and memory rows. | 2026-11-24 |

| 20 | Model scheduling without an answerable approval surface fails closed | A model-initiated create or semantic edit returns a durable `approval_required` proposal with no schedule write and no approval row. Operator resolution revalidates and commits; trusted direct operator scheduling remains direct and audited. This deliberately does not port upstream no-card auto-save. | 2026-11-25 |
| 21 | Scheduled scripts are operator-provisioned, restricted and opt-in | A scheduled script is an allowlisted executable path under the configured scripts root, not inline model-authored code or a sandbox. It uses an args array without a shell, a minimal environment, allowed-root workdir, timeout/byte caps and durable execution evidence; `automation.allow_scripts` defaults false. | 2026-11-25 |
| 22 | Native monitors are bounded public HTTP or restricted script checks | URL monitors use the existing public-address egress policy; script monitors use the restricted script runner. Model-supplied headers, cookies, userinfo, private-network targets, browser execution and JavaScript rendering are rejected. First success baselines, unchanged suppresses, change wakes, and failure preserves the last good baseline. | 2026-11-25 |
| 23 | Bot Chat and room delivery use honest native mappings | `bot-chat` and `bot-chat:<profile>` map to durable local conversations rather than byte-identical upstream profile semantics. `room:<id>` requires a room-capable adapter plus a configured default room channel; otherwise validation rejects it. `home`, `local:<id>` and object targets, if shipped, are documented LEO-native extensions. | 2026-11-25 |
| 24 | Delivery receipts and Telegram cards are transport-honest | Runtime delivery reuses the preview resolver and keys receipts by `platform:chat:thread`; legacy `{channel: target}` callers keep their projection and receipt keys. Local and named bot-chat targets append assistant notes to durable conversations with schedule/run metadata. Telegram approval bodies are literal plain text in lossless chunks; a body beyond the card cap becomes `deny_only` with the full text left in the dashboard, and threaded callbacks preserve their topic and schedule kind. | 2026-11-26 |
| 25 | Scheduled side effects cannot park an invisible approval | MEDIUM/HIGH outbound, browser, computer, plugin and shell calls from an unattended source are denied before `PermissionManager`; one durable needs-you notice is emitted and no approval row exists. Stored prompts are re-scanned at execution so a tampered job fails closed without reaching a model. Attended command approvals remain unchanged. | 2026-11-26 |
| 26 | Secret refusal is digest-only and intrinsic detection has no prefix catalog | Preflight precedes authorization, quota, dispatch and persistence; refused tools store a canonical digest and stable category/rule only. Vendor-less opaque tokens and private-key headers without an end marker are detected intrinsically, and every sink redacts those shapes even for non-opt-in tools. | 2026-11-26 |
| 27 | Schedule API mutations are bound to the authenticated operator | `LEO_API_TOKEN` is required when configured, Host/Origin/Sec-Fetch-Site are validated, and the audit actor is `api:<principal>`. Request-body channel/subject fields never grant authority; command-kind approval compatibility is deliberately preserved. | 2026-11-26 |
| 28 | No locale subsystem or prompt cache is simulated | LEO rebuilds its system prompt each turn and has no locale catalogs. Frozen centralized English copy plus DTO, event, API and UI contract tests replace those assumptions; they are documented as not implemented, not claimed as parity. | 2026-11-26 |
| 29 | Pause/resume are explicit tools and scheduling guidance is conditional | The final model roster has nine tools: explicit `schedule_pause` and `schedule_resume` wrap the one `ScheduleService.update` path with a bounded auditable reason, an expected config revision and the same edit card as any other model edit; pausing keeps the stored instant so a resume cannot re-anchor it. `automation.proactive_mode` defaults to `offer`; `off` removes only a short system-prompt hint and guidance appears only on a trusted turn whose surface can present, answer and rewrite a card. No mode bypasses consent or create grants. | 2026-11-26 |

Open assumptions: local-only mode is the default; network integrations remain
DISCONNECTED/BLOCKED until credentials are supplied by the user. The web
dashboard binds to localhost only.
